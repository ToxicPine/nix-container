# VMM choice and launch options

Status: July 2026. The benchmark runner is QEMU 11's x86 `microvm` machine on
KVM. This host is a single-NUMA-node AMD Ryzen AI 9 365 with AMD-V, 10 physical
cores, 30 GiB RAM, and a usable `/dev/kvm`.

The VM flake imports `fs/hm-base/npins` directly and evaluates NixOS with that
same `nixpkgs` source. There is no second nixpkgs flake pin: the VM and
container therefore use the exact same npins revision, hash, and package
versions.

## Selected launch path

`run-vm` uses direct Linux kernel and initrd boot. QEMU's `microvm` board is
intended for short-lived guests and boot/footprint measurement, has no PCI or
ACPI, and exposes only explicitly requested virtio-mmio devices. The command
uses:

- `-accel kvm -cpu host,-x2apic`: hardware virtualization and the real Zen CPU
  feature set, with x2APIC hidden because the pinned QEMU 11 `microvm` board
  stalls before the kernel entry point when this host feature is exposed.
  QEMU's `migratable=off` override is also omitted because it independently
  causes the same pre-entry stall on this host. Neither change affects the
  benchmark's one-vCPU topology, and cross-host migration is not used.
- one vCPU and 256 MiB by default: enough for this single-worker nginx case
  without adding idle vCPU threads or unrepresentative RAM. Both are explicit
  runner options and must be held constant across VM samples.
- private, demand-faulted RAM with `prealloc=off,merge=off,dump=off` by
  default: avoids touching all guest RAM during launch, keeps KSM out of the
  non-KSM result, and excludes RAM from accidental core dumps. The separate
  `--ksm` arm changes only `merge=on`, making guest RAM eligible for host KSM.
- `virtio-balloon-device,free-page-reporting=on`: keeps the configured 256 MiB
  fixed and visible to the guest while allowing Linux to report genuinely free
  pages for QEMU to discard from host residency. The legacy free-page-hint
  interface and target-driven `deflate-on-oom` behavior remain disabled. The
  ordinary inflation queue is not driven in the default or KSM arms, so the
  guest is not dynamically squeezed below its configured RAM. The separately
  labelled active-balloon arm uses `--qmp PATH` so the external harness can
  issue a standard QMP `balloon` target, followed by a fixed settling window.
- `microvm,pit=on,pic=on,rtc=on,isa-serial=on,x-option-roms=on`: retains the
  smallest legacy boot set that works efficiently on this host. QEMU permits
  removing PIT/PIC only when the host CPU supplies `TSC_DEADLINE`; this Ryzen
  does not, and disabling them prevents the guest kernel from progressing.
  Disabling RTC works but adds roughly 1.3 seconds to measured readiness while
  the guest waits for unavailable wall-clock state. The ordinary upstream
  NixOS kernel artifact is a compressed `bzImage` and does not enter the kernel
  when option ROM loading is disabled. The scripted NixOS initrd also requires
  a usable kernel console to progress reliably; the headline serial backend is
  therefore `null`, which instantiates the port but discards all output.
  `auto-kernel-cmdline=on` supplies the virtio-mmio discovery parameters.
- `-nodefaults -no-user-config -display none -monitor none`: no implicit
  devices, GUI, or monitor. `--console FILE` changes the otherwise-null ISA
  serial backend to a diagnostic file without changing the guest device model.
- one `virtio-blk-device` over a prepared qcow2 overlay. The file backend uses
  `aio=io_uring`; host caching stays enabled so repeated instances can share
  cached reads of the immutable raw backing image. Flushes remain enabled.
  Discard passes through to release overlay clusters.
- one `virtio-net-device`. The reproducible default is restricted QEMU user
  networking with only a loopback host-forward to nginx, but this is a
  diagnostic convenience path. Headline readiness and load runs use `--tap`
  with an already-created TAP device plus vhost-net, a unique static guest
  CIDR, and a unique unicast MAC. TAP/bridge creation and address allocation
  are outside launch timing; DHCP and NAT are not used.
- `-no-reboot` plus the guest's `reboot=t` gives a quick, deterministic QEMU
  exit. QEMU's seccomp `-sandbox` option is not used: with the pinned QEMU 11
  build it prevents this io_uring-backed guest from reaching readiness even
  with only the default sandbox policy. KVM remains the VM isolation boundary.

[QEMU invocation](https://www.qemu.org/docs/master/system/invocation.html),
[QEMU virtio devices](https://www.qemu.org/docs/master/system/devices/virtio/index.html),
and [QEMU qcow2 tooling](https://www.qemu.org/docs/master/tools/qemu-img.html).

## Image and instance tradeoffs

The base disk is generated by NixOS's upstream `image/repart.nix` module, not
`nixos-generators`. It contains the NixOS closure, a functional multi-user Nix
installation and daemon, nginx, and its systemd unit in a minimized ext4 GPT
root partition. The kernel and initrd are exported beside that raw image for
direct boot.

The configuration imports NixOS's upstream `profiles/minimal.nix` module. It
also disables the channel, automatic garbage collection, automatic store
optimisation, D-Bus, NSS module loading, systemd-oomd, timesyncd, udisks, and
the default package set. These are safe for this self-contained benchmark and
remove boot services and closure paths while retaining systemd, the Nix daemon,
the Nix client, a writable store/database, networking, and nginx.

The upstream `profiles/perlless.nix` profile was evaluated but is not used: in
this pinned NixOS revision it requires systemd initrd and fails with the
working scripted-initrd path. `profiles/bashless.nix` is inapplicable because
it disables Nix, violating the internal package-management requirement.

`prepare-vm` creates one qcow2 overlay per instance, with the immutable Nix
image as a raw backing file. This is cheap and keeps all guest writes isolated.
The qcow2 metadata uses 64 KiB clusters, extended L2 subclusters, lazy
refcounts, and metadata preallocation. A fresh overlay occupies about 584 KiB
on this filesystem; metadata allocation is completed before timing and
extended L2 limits copy-on-write amplification. An unclean host crash can
require `qemu-img check`, which is acceptable for disposable benchmark
instances. Preparation, including qcow2 creation, is never performed by
`run-vm`. Backing-file validation also belongs in preparation or benchmark
preflight, not in the timed launcher; `run-vm` therefore does not invoke
`qemu-img` or `jq` before QEMU.

Keeping the host page cache enabled is deliberate: both targets may benefit
from warm host caching. VM code and file data must still enter each guest's
private RAM and guest page cache. gVisor instances can consume the same cached
read-only lower-store pages without a separate guest kernel or guest page
cache. Free-page reporting is part of the production-like baseline because
production VM stacks reclaim unused guest pages; do not issue active balloon
inflation targets during a sample. KSM is off in headline samples and enabled
only with `run-vm --ksm` in the separately reported KSM arm.

## Rejected alternatives

- Firecracker has a smaller device model and an excellent startup focus, but
  on x86 it requires an uncompressed ELF `vmlinux`, while the ordinary upstream
  NixOS kernel output is a bootable `bzImage`. It also adds API/jailer and TAP
  setup to this prototype. QEMU microvm accepts the stock NixOS kernel, remains
  in QEMU's supported virtualization security set, and is already packaged by
  the pinned nixpkgs.
- Cloud Hypervisor is a strong modern KVM VMM, but its broader PCI-oriented
  cloud device model brings no advantage to this one-disk/one-NIC workload and
  would add another runner-specific boot contract.
- QEMU `q35` and UEFI/SeaBIOS were rejected because firmware, ACPI, PCI, and
  device enumeration add launch work that this Linux-only benchmark does not
  need.
- `cache.direct=on`, RAM preallocation, huge pages, and `cache.no-flush=on`
  were rejected. Direct I/O defeats the warm-page-cache comparison;
  preallocation moves all RAM cost into startup; huge pages require host
  reservation and inflate small guests; disabling flushes risks corrupting
  prepared instances.
- Snapshot/restore was rejected because it skips guest kernel and service boot,
  changing the isolation-startup workload being compared.
- Pinned nixpkgs exposes a 396 MiB uncompressed `vmlinux` in the kernel's
  development output. Stripping debug data reduces it to about 55 MiB, but that
  ELF did not reach service readiness with option ROMs disabled. The supported
  `tinyconfig` and u-root kernels cannot run this package-managed NixOS
  userspace. A bespoke manual kernel was therefore rejected in favour of the
  proven 13 MiB upstream `bzImage` path.
